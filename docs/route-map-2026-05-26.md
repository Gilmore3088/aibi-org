# Route Map

Snapshot of every `page.tsx` under `src/app/` on the
`feature/redesign-mockup-system` branch, with the design system each
page is wearing, whether it's gated, and whether it's indexable. The
point: surface duplicate concepts, leaks, and stale pages left over
from a sprint that migrated a lot of surfaces to the new "mockup"
design system at the same time.

## TL;DR

- **89 page routes** found under `src/app/**/page.tsx` (counting
  dynamic segments as one route each)
- **~32 public marketing routes** (home, marketing essays, course
  marketing, FAQ, briefing, playbooks, research, etc.)
- **~28 signed-in interior routes** (dashboard, foundation program
  LMS, my-toolbox, practice, in-depth dashboard)
- **~15 internal / preview / utility routes** (preview-home,
  user-home, lms-preview, design-system, redesign-audit,
  redesign-checklist, foundation-preview, coming-soon, verify,
  legal pages)
- **8 confirmed conflicts** — listed below. Two are urgent: `/faq`
  and `/briefing-preview` were converted to public marketing pages
  on this branch but their old internal-bundle behaviour on `main`
  was `robots: noindex`. **The new versions do not set `noindex`,
  so once this branch merges they will be indexable public pages
  with the same URLs that internal docs and old emails point at.**

## Confirmed conflicts

### 1. `/faq` — internal HTML bundle on `main`, public marketing on this branch

- `git show main:src/app/faq/page.tsx` reads a hand-written HTML
  bundle, sets `description: 'Internal FAQ reference. Not for
  external distribution.'` and `robots: { index: false, follow: false }`.
- This branch: `src/app/faq/page.tsx` imports `MockupShell` from
  `@/components/mockup` and renders a public FAQ page. Its
  `metadata` export has a public title and description; **no
  `robots: noindex`**, so Google will index it.
- **Recommendation:** decide whether the public FAQ replaces the
  internal one outright, or whether the internal one needs to move
  to a different path (e.g. `/internal/faq`). If the public version
  is intended, kill the old `_body.html` / `_script.js` bundle, the
  `rewriteBundleLinks` import, and confirm copy is final. Either
  way, audit external links (emails, internal docs) for the old
  meaning of `/faq`.

### 2. `/briefing-preview` — internal results-page preview on `main`, public marketing on this branch

- Same pattern as `/faq`. On `main` it's a noindex internal preview
  of the assessment results briefing. On this branch it's a
  MockupShell page with public-facing copy and **no `noindex`**.
- **Recommendation:** if the public surface needs to live, rename
  it (e.g. `/assessment/briefing` or fold into `/results`) and
  leave `/briefing-preview` as the internal preview with its
  noindex header. The current state will index the briefing
  preview URL into Google and confuse internal links.

### 3. `/playground` vs `/practice` — two sandbox surfaces

- Both shipped intentionally per `project_sandbox_two_surfaces_2026_05_26`.
- `/playground` — public marketing sandbox (mockup system, public).
- `/practice` and `/practice/[repId]` — signed-in "interior" practice
  surface (mockup system, but neither file gates on Supabase auth in
  the page — gating presumably happens in a parent layout or via
  enrollment lookups upstream).
- **Status:** intentional, but the page copy needs to clearly
  differentiate the two so a visitor and an enrolled learner each
  land on the right one. Verify the home / dashboard CTAs point at
  the right of the two.
- **Recommendation:** add a one-sentence eyebrow on each
  ("Public sandbox — open to anyone" vs "Practice — your enrolled
  workbench") so the distinction is unambiguous. Confirm a
  signed-in user is not shown a CTA to `/playground` (and vice
  versa).

### 4. `/my-toolbox` vs `/dashboard/toolbox` — two "toolbox" surfaces in two design systems

- `/my-toolbox` is mockup-system, signed-in, with a skill-builder
  and `/my-toolbox/skills/[slug]`.
- `/dashboard/toolbox` is **ledger-system** (legacy), signed-in,
  with `library/` and `cookbook/` subroutes.
- A redirect exists `/toolbox → /dashboard/toolbox` from the
  2026-04-29 IA decision. There is **no** redirect from
  `/dashboard/toolbox → /my-toolbox` or vice versa.
- **Recommendation:** pick one. The mockup-system `/my-toolbox` is
  the redesign target; either retire `/dashboard/toolbox` (and
  port its `library` + `cookbook` subroutes under `/my-toolbox/`)
  or wire 308s from `/dashboard/toolbox*` to the corresponding
  `/my-toolbox` paths. Today, the two are reachable simultaneously
  and visually inconsistent.

### 5. `/preview-home` vs `/user-home` vs `/` — three "home-ish" routes

- `/` is the public homepage (mockup system, indexable).
- `/preview-home` — `robots: noindex`, 35 lines, looks like a
  design preview stub.
- `/user-home` — `robots: noindex`, 20 lines, looks like a stub for
  what a signed-in user home would be.
- **Recommendation:** these are dev surfaces left behind by
  iterations. If `/dashboard` is now the signed-in home, retire
  `/user-home`. If `/preview-home` is no longer needed for design
  review, delete it. Both are noindex so the risk is low, but they
  add ambient confusion.

### 6. `/courses/foundation` vs `/courses/foundation-preview` vs `/courses/foundation/program`

- `/courses/foundation` — `redirect('/courses/foundation/program')`
  on the server, so any link resolves to the program.
- `/courses/foundation-preview` — noindex, 23 lines, design preview
  of the course landing.
- `/courses/foundation/program` — the actual LMS interior, gated by
  `getEnrollmentResult()`. Still on the **ledger** design system.
- **Buyer path:** there is no public marketing page for the
  Foundation course on this branch — `/courses/foundation` 308s
  directly into the gated LMS, which immediately redirects to
  purchase. That's a gap.
- **Recommendation:** restore a public-marketing landing at
  `/courses/foundation` (mockup system) that sells the course and
  CTAs to purchase, then preserve the preview at
  `/courses/foundation-preview`. Or delete the preview if the
  marketing page replaces it.

### 7. `/redesign-audit` vs `/redesign-checklist` — two internal QA surfaces

- Both noindex. `/redesign-audit` lists every route with what
  sketch it's based on and migration notes (684 lines).
- `/redesign-checklist` is the operator checklist (644 lines) and
  uses `LedgerSurface` — i.e. it has not itself been migrated.
- **Recommendation:** keep both during the sprint; delete after
  merge. Make sure neither is linked from the public nav.

### 8. `/resources/*` vs `/research/*` — two content libraries

- `/resources` is **terra-legacy** (uses `--color-terra` and
  `--color-parch`). Has six essay slugs:
  `ai-governance-without-the-jargon`, `members-will-switch`,
  `six-ways-ai-fails-in-banking`, `the-skill-not-the-prompt`,
  `the-widening-ai-gap`, `what-your-efficiency-ratio-is-hiding`.
- `/research` is **ledger** (uses `--ledger-accent`). Index + a
  `[slug]` dynamic route. `next.config.mjs` 308s **only** the
  `/resources` root to `/research`; the individual essay URLs
  (`/resources/<slug>`) **still resolve to the old terra-legacy
  pages**.
- **Recommendation:** decide whether the essays move to
  `/research/<slug>` (Phase 07 was supposed to port them per the
  next.config comment but it hasn't shipped). Either way, both
  index and per-essay paths need to land on the same system. The
  current state means `/resources` redirects but `/resources/<slug>`
  doesn't — visitors landing on an essay link in an older email
  get terra-legacy styling on a page whose siblings are gone.
