TL;DR

  • All eight remaining modules (5–12) shipped as self-contained HTML experience mockups + markdown takeaways. Total ~6,762 lines of new module HTML, ~582 lines of learner-take-home markdown.
  • Curriculum fidelity is high. Signature lines and saved-card text match the locked spec verbatim. No emoji, no banned marketing words at the prose level, no PII patterns.
  • Three deviations are material: M3 ships its own internal $295 paywall overlay (collides with the locked free-with-email split); M4 carries the largest volume of literal <em> tags in JS-rendered lab body strings; M5 uses the banned word "leverage" in body copy.

  • Auth is sound. The preview-bypass production hard-floor is intact. No AiBI-P brand-string leaks in production code (one grep hit was a false positive in AiBI-Prompt-Cards).

Gate, auth, and certificate

Live code · read-only inspection

Free → email → paid staircase: not implemented

The locked spec (docs/foundation-course-modules.md lines 17–22) calls for M1 free-no-login, M2–3 free-with-email, M4–12 paid $295. The live code at src/app/courses/foundation/program/[module]/page.tsx:85–92 enforces a single binary gate: any visitor without a course_enrollments row is bounced to /purchase, regardless of which module they hit.

  • No anonymous-M1 path. No FREE_MODULES or isFree config anywhere in src/lib/lms/.
  • No email-only soft-enrollment surface for M2–3. Implementing the staircase needs a new gate path — most likely a course_email_captures table and an enrollment-with-tier read.
  • The M3 mockup carries its own client-side $295 overlay; this is UI-only and is not enforced server-side.

Auth: sound

src/lib/auth/previewBypass.ts exists and the production hard-floor at line 18 (if (process.env.VERCEL_ENV === 'production') return false;) refuses unconditionally. course/program/layout.tsx:40 calls isPreviewAuthBypassEnabled() and short-circuits with return <>{children}</> before any redirect logic. Onboarding and forward-only progression gates are intact.

Certificate path: not auto-triggered

src/app/api/courses/save-progress/route.ts validates, authenticates, enforces forward-only completion, updates completed_modules + current_module, and returns { success: true, nextModule }. It does not call generate-certificate. The only caller of generate-certificate is the user clicking a download link on the certificate page (certificate/page.tsx:255). A learner who finishes M12 will not have a certificate row created or a transactional email sent unless they manually navigate to the cert page.

Banned brand strings: clean

One grep hit for AiBI-P in src/app/api/prompt-cards/download/route.ts:7 — false positive (the substring matches AiBI-Prompt-Cards.pdf). No AiBI-Practitioner anywhere. No live code carries the banned designation.

Launch blockers · Slice 1

From Plans/foundation-course-unified-rebuild.md

BLOCKER 01 · Certificate not auto-triggered on M12 completion

Wire generate-certificate from save-progress/route.ts on the final-module write.

Gated on allModulesComplete(completed_modules) (reuse submit-work-product/route.ts:53). Required for the completion-based cert that the launch spec v2 promises. Without this, M12 is the most disappointing moment in the course — the learner finishes and nothing happens.

BLOCKER 02 · Free / email / paid tier split not implemented

Decide between spec-as-written (three tiers) or single-paywall reality (one tier at M1).

If the spec stands, the gate logic in [module]/page.tsx and _lib/courseProgress.ts needs a tier-aware path that lets unauthenticated users land on M1 and email-only users land on M2–3. Currently any non-enrolled visitor is bounced to /purchase regardless of which module they hit — which blocks the lead-capture funnel the spec was designed around.

BLOCKER 03 · M3 internal paywall overlay vs. server-side gate

Reconcile M3's client-side $295 overlay with the actual paywall surface.

If the conversion finale is meant to land at M3 (per the memory note), the spec needs an update and the M4–12 gate stays paid. If M3 stays free-with-email, the overlay comes out of the mockup. Owner decision needed before Slice 1 ships.

BLOCKER 04 · M12 certificate descriptor sentence verification

Confirm the spec-mandated sentence is on the certificate face.

Spec line 455: "[name] can use AI thoughtfully, safely, and practically in real banking work — and has the system to keep getting better at it." The title AiBI-Foundation is present; the full descriptor needs a closer read of the cert SVG/HTML block in module-12-experience.html. If absent, the finale's credibility moment is hollow.

CLEANUP 01 · Literal <em> sweep (M4, M5, M9, M12)

Strip literal italic tags before implementation port.

Not a release blocker — the site-wide CSS rule strips visual italics — but source non-compliance with the italics-retired standard. Easiest to clean in the same sweep that lands the M4–12 production build.

Open questions for the owner

  1. M3 paywall: free-with-email per spec, or "$295 conversion finale" per the memory note? Pick one before implementation port.
  2. M10 "the unlock" — keep as a spec-protected signature or rename to something off the banned list?
  3. M5 Brief response-builder — currently varies prose on tone + flag-rule; treats role/institution/guardrail as signature metadata. Acceptable, or should role-specific paragraphs swap too?
  4. M11 Toolkit "Most used / This week / Favorites" — hard-coded in the mockup. Wire to real usage telemetry when M11 ports, or stay decorative?
  5. M12 certificate ID — generated client-side per session in the mockup. The production path needs server-issued IDs tied to enrollment.
