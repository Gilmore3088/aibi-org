## Findings

### Finding 1 — Course-route gate is inconsistent with `/dashboard` gate ❌

**Severity:** **High — blocks launch checklist §3.85.**

**Where:** [`src/app/courses/foundation/program/[module]/page.tsx`](../../src/app/courses/foundation/program/[module]/page.tsx) line ~80–86, via [`src/app/courses/foundation/program/_lib/getEnrollment.ts`](../../src/app/courses/foundation/program/_lib/getEnrollment.ts).

**What happens:**
- `/dashboard` (and the rest of the dashboard tree) correctly redirects
  unauthenticated requests to `/auth/login?next=/dashboard`. See
  [`src/app/dashboard/layout.tsx`](../../src/app/dashboard/layout.tsx).
- `/courses/foundation/program/[module]` redirects unauthenticated
  requests to `/courses/foundation/program/purchase` instead. Reason:
  `getEnrollment()` collapses both "no auth session" and "auth session
  but no enrollment" to the same null return, and the page treats null
  uniformly as "send to purchase."

**Why this is wrong:**
1. The two states are different. An unauthenticated visitor should be
   sent to `/auth/login` with `?next=` so they land back on the course
   after signing in. A logged-in non-enrollee should land at `/purchase`.
2. The launch checklist (§3.85) explicitly requires the `?next=` pattern
   for deep links — currently broken.
3. Security: the purchase page leaks course-existence information to
   unauth visitors; the login redirect would be more private.

**Recommended fix:**
- Modify `getEnrollmentResult()` (or add a sibling) to surface a
  distinct `unauthenticated` branch.
- In `[module]/page.tsx`, branch: `unauthenticated → redirect('/auth/login?next=...')`,
  `not_enrolled → redirect('/courses/foundation/program/purchase')`.
- Audit sibling routes for the same pattern:
  `/courses/foundation/program/{onboarding, settings, purchase, gallery,
  certificate, submit, post-assessment, artifacts/[artifactId]}` and
  `/assessment/in-depth/{take, dashboard, purchased}`.

**Verification after fix:**
- `curl -I -o /dev/null http://localhost:3000/courses/foundation/program/3`
  should return `307 → /auth/login?next=%2Fcourses%2Ffoundation%2Fprogram%2F3`.
- Re-run `npx playwright test e2e/auth.spec.ts --grep "§3.85"` — expect pass.

### Finding 2 — Local `.env.local` is missing Supabase keys ⚠️

**Severity:** Low (environmental, not a code bug) — but **blocks full local E2E**.

**Where:** `.env.local` has only `COMING_SOON` set; no
`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, or
`SUPABASE_SERVICE_ROLE_KEY`.

**Impact:**
- All E2E tests that exercise real auth flows (signup, login,
  password reset, magic link round-trips, logout) cannot run locally.
- The form submit on `/auth/login` currently displays
  `"Auth is not configured. Set Supabase environment variables."`
  rather than the production-realistic "Invalid credentials" error.
- The dashboard layout `if (!isSupabaseConfigured()) redirect(loginHref)`
  is hitting the fail-closed path, not the real auth path. The redirect
  works for §3.62 because the fallback also redirects to login — but
  this is **accidentally passing the test for the wrong reason**.

**Recommended fix:**
1. Add the three Supabase keys to `.env.local` from Vercel:
   `vercel env pull .env.local --environment=development` (or copy from
   the staging/production Vercel project, treating local as a third
   environment).
2. Add `E2E_ALLOW_PRODUCTION_SUPABASE=true` if you want to run the
   seeded suite locally — note this creates real test users in the
   production Supabase project under
   `e2e+*@aibankinginstitute.test` (RFC 6761 reserved TLD; never
   reaches a real inbox; cleaned up automatically by `cleanupSeededUser`).
3. Re-run the full suite: `npx playwright test e2e/auth.spec.ts`.

### Finding 3 — `/api/auth/me` returns 200 with `user:null` when unauth (intentional, but launch checklist disagrees)

**Severity:** Decision needed.

**Conflict:**
- Code comment in [`src/app/api/auth/me/route.ts`](../../src/app/api/auth/me/route.ts)
  explains: "Never errors on missing config — clients should treat null as
  'not logged in or service unavailable.'" Returns 200 always.
- Launch checklist §3.75 requires: `/api/auth/me` returns **401** when
  not authenticated.

**Resolution paths:**
- (a) Update the launch checklist to match the code (200 + null) — the
  code's reasoning is sound for the use case (client-side gating without
  needing error handling for the unauth case).
- (b) Update the code to return 401 — matches REST norms and makes the
  endpoint behave as documented in the checklist.

I'd lean (a) — the code's design is deliberate and well-commented; it's
the checklist that's drifted. Either way, get them in sync.

## What's strong (worth keeping)

The auth implementation has several intentional, well-commented
defenses worth calling out:

1. **Email-scanner pre-fetch defense** ([`callback/route.ts`](../../src/app/auth/callback/route.ts) lines 12–22).
   GET never consumes a token — it bounces to the `/auth/confirm`
   interstitial. Only the user's deliberate click triggers POST →
   `verifyOtp`. Solves the documented Outlook/Apple Mail/Gmail token-burn
   bug from 2026-05-11.

2. **Cookie propagation across redirects** ([`callback/route.ts`](../../src/app/auth/callback/route.ts) lines 24–32).
   Cookies are captured during the auth call and written directly to the
   `NextResponse.redirect()` object. Without this, `verifyOtp` would
   succeed server-side but the browser would never receive cookies and
   the user would land logged-OUT despite a working link.

3. **Open-redirect defense** ([`auth.ts:sanitizeNext`](../../src/lib/supabase/auth.ts) lines 11–21).
   Rejects protocol-relative URLs, absolute URLs, and embedded newlines.
   Falls back to `/dashboard`. Used at every redirect entry point.

4. **Session refresh in middleware** ([`middleware.ts`](../../src/middleware.ts) lines 96–122).
   `supabase.auth.getUser()` triggers token refresh near expiry, on
   every request. Cookies are written onto both the request (so
   downstream Server Components see them) and the response (so the
   browser receives them).

5. **Server-side gate on `/dashboard` tree** ([`dashboard/layout.tsx`](../../src/app/dashboard/layout.tsx)).
   Per the PR #121 fix, the gate is enforced before any `/dashboard/*`
   page renders, not in client-side useEffect. Right pattern.
