Section 1 - Operating principle

AI prepares. Bankers decide. Evidence proves.

Core rule

AI can draft, summarize, convert, compare, and critique. A banker owns the input, the approved source, the human review, the final use, and the retained evidence.

This guide is not generic prompt engineering. It is banker prompting: choose the right prompt type, use approved source material, replace sensitive facts with placeholders, ask for draft support instead of decisions, mark uncertainty with [VERIFY], and route higher-risk work through review.

Use this foundation before a one-off prompt becomes a repeatable team asset. If the prompt is reused by others, move it into the Workflow SOP Builder so the tool, allowed inputs, reviewer, approval checkpoint, escalation path, and retention rule are documented.

The Banker Prompt Formula

Role

Who should AI act as?

Name the banking role or review lens.

Task

What should it produce?

Ask for draft support, not a final decision.

Source

What approved material should it use?

Point to public, internal, redacted, or synthetic source material.

Constraints

What must it not do?

No invented facts, rates, fees, legal conclusions, or policy changes.

Output

What format should it use?

Choose bullets, table, checklist, email, memo, SOP, or FAQ.

Verify and escalate

What needs review?

Mark uncertain items [VERIFY] and name the escalation trigger.

Section 2 - Prompt types

Pick the work before writing the prompt.

Most banker prompts fit one of these types. Each type should state safe inputs, prohibited inputs, output format, review rule, and example language.

Section 3 - Safe inputs and placeholders

Replace real specifics before the prompt.

The safest prompting habit is to strip sensitive specifics before asking AI for help. Use uppercase bracketed placeholders consistently across the bank's prompt library.

Sensitive itemUse placeholderNotes
Customer name[CUSTOMER]Use fictional names only in training scenarios.
Account number[ACCOUNT_NUMBER] or [ACCOUNT_LAST4]Never paste the real account number into a public tool.
Balance or amount[BALANCE], [AMOUNT], [AMOUNT_RANGE]Ranges are safer than exact values for examples.
Transaction[TRANSACTION] or [TRANSACTION_PATTERN]Use aggregate or pattern-level language where possible.
Complaint[COMPLAINT_SUMMARY]Remove identity, account, and specific event details unless the tool is approved.
Credit reason[HUMAN_PROVIDED_REASONS]AI may clarify language; it does not choose principal reasons.
BSA/AML case facts[SYNTHETIC_CASE_FACTS]Use fictional facts for training. Do not paste real SAR, alert, or investigation facts into public tools.
Credentials[CREDENTIAL]Passwords, API keys, tokens, and authentication details are Red.

Default stop rule

If the prompt contains a real customer, account, transaction, complaint, SAR/AML detail, credential, examiner-sensitive fact, or regulated decision, stop and classify higher before using AI.

Section 4 - Risk lanes

Classify before generating the final prompt.

Green - allow prompt generation

Public, synthetic, or non-sensitive internal work. No real customer data. No regulated decision. Output stays internal or receives routine human review.

Yellow - approved tool plus named reviewer

De-identified or internal data, customer-facing draft, examiner-facing draft, policy, risk, procedure, or retained business record. Generate only after the user confirms approved tool, reviewer, and output review.

Red - block public-tool prompting

Public tool with NPI, account records, SAR/AML detail, credit decisions, adverse action, authentication, fraud conclusion, legal/compliance determination, credentials, or production access. Route to an approved enterprise workflow or specialist review.

Safe versus unsafe examples

UnsafeSafer
Summarize a named customer's checking account dispute with account number, balance, and debit card transactions.Using placeholders, draft an internal service summary. Do not decide. Mark missing facts [VERIFY]. Customer: [CUSTOMER]. Account: [ACCOUNT_TYPE]. Issue: [DISPUTE_SUMMARY].

Improve a real SAR narrative from the case system.Using fictional case facts only, organize a SAR narrative training example into who, what, when, where, why, how, missing facts, and reviewer checklist.
Section 5 - Copy-ready working prompt

Use this pattern for safe first drafts.

You are assisting [ROLE] with [TASK]. Use only this source material: [PUBLIC / INTERNAL / REDACTED / SYNTHETIC SOURCE DESCRIPTION]. Do not use or request customer names, account numbers, balances, transaction-level details, SSNs, DOBs, complaint specifics, SAR/AML case details, authentication details, credentials, production system details, or examiner-sensitive material. Produce: [BULLETS / TABLE / CHECKLIST / EMAIL DRAFT / SCRIPT / FAQ / SOP / MEMO]. Constraints: Do not invent facts. Do not make a decision. Do not add requirements. Preserve source meaning. Mark uncertain or unsupported items as [VERIFY]. Label output as draft pending review. Human review: [REVIEWER] confirms source accuracy, data handling, unclear items, and final-use approval. Escalate if customer impact, credit, BSA/AML, fraud, authentication, complaints, examiner-facing material, legal/compliance interpretation, or prohibited data appears.

Review checklist before copying output downstream

  • Sensitive data was removed or replaced with placeholders.
  • The tool is approved for the data class used.
  • The prompt asked for draft support, not a final decision.
  • The output is in the requested format.
  • Numbers, dates, citations, policy claims, and procedural steps were checked against source documents.
  • Uncertain items are marked [VERIFY].
  • Customer-facing, examiner-facing, regulated, or retained output has a named human reviewer.
  • Escalation triggers are clear.
  • Final version and evidence are retained where required.
